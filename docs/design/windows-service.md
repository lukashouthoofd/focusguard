# Windows enforcement service design

Status: Windows service prototype with an opt-in desktop client. `focuser-app::protocol` defines typed request/response envelopes, bounded synchronous framing, and Tokio async framing with a 1 MiB payload cap. `crates/focuser-service` has an SCM entry point, a console test mode, and a local byte-mode named-pipe server. Its opt-in policy mode opens a persistent SQLite database, accepts a narrow set of domain-policy commands, and reconciles enabled domain rules as apex and `www` hosts entries into an injected hosts-file path. The reusable `focuser-client` crate opens that pipe with bounded retries and response deadlines, checks that SCM reports the server PID as the running, own-process `FocusGuardService`, and correlates the response to its request ID. The Tauri UI selects service mode when `--service-client` is supplied or SCM finds a registered service; it skips the local database and workers and reports service errors without falling back. A shared exclusive UI-owner file handle prevents local and service UI processes from running concurrently and is released by the OS after exit or crash. The service-only policy screen manages block lists and enabled domain rules and reports the limited health data available. It is not wired into the installer. An installer must stop pre-existing local UI instances before starting the SCM service; the current UI lock cannot coordinate with a service installed while a pre-existing local process is already running. A Windows pipe integration test covers custom-host process-ID matching, mismatch rejection, and command execution; it does not test the SCM identity path or run under the installed service. The service object's `SERVICE_QUERY_STATUS` access for standard users still needs installer and VM verification. The service cannot enumerate deeper subdomains, and hosts entries do not express URL paths. SCM startup requires the initial policy apply to succeed before it reports `Running`. Windows tests use temporary databases and hosts files; the service was not installed, and no machine-wide policy was changed. SCM execution and actual hosts-file permissions, DNS behavior, and recovery remain unverified.

### CI-only SCM recovery smoke test

`.github/workflows/ci.yml` has a Windows Server 2022 job that builds the service and a small authenticated IPC probe, then runs `scripts/windows-service-recovery-smoke.ps1`. The script refuses to run outside a GitHub-hosted Windows runner (`GITHUB_ACTIONS`, `RUNNER_OS`, and `RUNNER_ENVIRONMENT`), requires an elevated runner token, refuses to reuse an existing `FocusGuardService`, and creates only a unique directory under `RUNNER_TEMP`. It registers the service as LocalSystem with a service SID and SCM restart-on-failure actions, passes temporary database and hosts-fixture paths, creates and explicitly enables an exact-domain rule through `focuser-client::execute`, forcibly terminates the service process, waits for it to stop, clears the fixture before the delayed recovery action, then waits for a different SCM-reported PID and checks through authenticated IPC and the fixture file that the rule persisted and was reapplied after restart. A PowerShell `finally` block stops/deletes the test service and removes its bounded temporary directory.

The service reports increasing SCM startup checkpoints around argument parsing, service-SID validation, database open, initial policy reconciliation, runtime creation, and pipe setup. The smoke script prints those checkpoints and captures the final SCM state, temporary fixture/database metadata, and recent service-control events on startup timeout. The first hosted run (`42485936787`) built the service and created it successfully, but it remained `START_PENDING` for the script's 45-second deadline; the client probe and crash-recovery portion therefore did not run. The next run must identify the stalled startup phase and pass before this is considered runtime-verified.

This provides CI evidence only for the GitHub-hosted Windows Server 2022 runner and this exact-domain service mode: LocalSystem startup, named-pipe client identity verification, SQLite persistence, abrupt process termination, SCM recovery, and a write to the supplied hosts-file fixture. The service's real `ipconfig.exe /flushdns` path also flushes the ephemeral runner's DNS cache during startup and policy changes; the test does not assert name resolution. It intentionally does not touch the runner's real hosts file or perform a network check. It does not verify the product installer, another Windows release, standard-user installation ACLs, DoH/VPN/proxy bypasses, local-administrator resistance, or tamperproof security. The actual SCM test is not part of local test runs; the PowerShell script and IPC probe are gated to the GitHub-hosted Windows environment.

## Why a service is required

In normal local mode, the UI opens the SQLite database in `crates/focuser-ui/src/main.rs`, builds `AppContext`, then starts the blocker, API server, and foreground watcher as threads. `crates/focuser-ui/src/blocker.rs` performs hosts synchronization, app-process enforcement, extension monitoring, allowance work, and uninstall monitoring. Closing or crashing that process stops those checks. The `--service-client` mode avoids that local state and worker startup, and normal Windows startup also selects service mode when SCM finds the service registered. Both UI modes take the same exclusive per-user owner handle. The installer must stop any already-running local UI before it starts the service, since a running service and an older local UI are separate processes. The current NSIS Scheduled Task launches at logon with `/rl highest`; this is not an SCM service and does not restart a process killed after login. A service-mode installer must replace or update that task so the interactive UI runs unelevated, then verify the task principal and launch mode in a disposable VM.

`crates/focuser-common/src/ipc.rs` contains shared service messages and the versioned pipe name. The service server and authenticated Windows client exist as prototypes, and the desktop command/UI path can use explicit or SCM-detected service mode. The legacy native-messaging crate is not the service transport: it targets a loopback port and its protocol must not be reused unchanged.

## Smoke host

On Windows, run `cargo run -p focuser-service -- --console` to start the in-memory smoke host as the current user; its pipe accepts only the `AppVersion` probe. The opt-in persistent policy mode takes explicit paths: `cargo run -p focuser-service -- --console --database <PATH> --hosts-file <PATH>`. Use a disposable hosts-file fixture for manual tests; this mode edits the path supplied. The pipe permits only block-list, domain website-rule, schedule, apply, health, and version operations. Policy mode rejects extension-only website rule kinds and does not permit a transient remove that would be undone by the next reconciliation. Console mode uses the current process SID and provides no privilege separation. The executable has an SCM dispatcher that requires owner SID, database, and hosts-file configuration, but this repository has no service installer action or end-to-end SCM test. `cargo test -p focuser-service --locked` exercises the local pipe ACL, probe, denied mutation, mismatched caller SID, invalid frame, first-instance behavior, policy persistence, exact-domain reconciliation, rejected unsupported commands, and injected write/DNS-flush failures on Windows.

The service screen can be started with `cargo run -p focuser-ui -- --service-client`. It expects the installed `FocusGuardService` SCM service and its configured pipe ACL; it does not connect to the console smoke host. Normal Windows startup also selects service mode when SCM finds a registered service, even if it is stopped. If the service is unavailable or another UI process holds the owner lock, the command view reports an error and must not open the local database. Do not install the service on a normal workstation for this smoke path; SCM authentication and service-account behavior still require a disposable VM.

## Ownership model

1. A Windows SCM service owns the policy database, rule engine, lock state, schedules, allowances, hosts changes, process checks, and browser-extension API. It restores policy from committed state before accepting requests after boot or recovery.
2. The production desktop app will run unelevated as a typed client. The current `--service-client` path skips the local policy database and enforcement workers, reports connection errors without fallback, and exposes only the service's narrow domain-policy UI. Normal startup remains local mode until installer, migration, and service verification are complete. The production UI must not run a parallel enforcement loop.
3. The first service install records one owner SID and uses one policy database under a service-controlled `ProgramData\PublikHQ\FocusGuard` directory. The UI has no direct write access. The service authenticates the pipe client SID and maps requests only to the configured owner's database and process session. Requests from other Windows users are denied; multi-user policy is deferred until cross-session isolation is implemented and tested.
4. The browser extension continues using the loopback API so URL/path rules can work while the UI is closed. The service hosts the API. It accepts only the installed FocusGuard extension origin for browser access, validates every request, and rejects mutations that conflict with a stored lock. Origin validation is not authentication against another local process; any endpoint whose misuse could weaken a lock needs a per-user credential or must not be exposed over HTTP.

The database move requires a versioned migration from the current per-user app data path. The service must perform the migration once, verify it, and preserve a recoverable backup before switching authority. No data migration is planned from upstream Focuser installs.

## Local IPC boundary

- Use a local named pipe with remote clients rejected. The SCM pipe DACL gives the unique `NT SERVICE\FocusGuardService` SID, LocalSystem, and administrators full pipe control; the configured owner SID gets the individual data/attribute rights needed by clients without `FILE_CREATE_PIPE_INSTANCE`. It verifies the impersonated caller's user SID on each connection rather than trusting a pipe name. Administrator and LocalSystem access are intentionally trusted; LocalSystem processes can also create pipe instances.
- Supply an explicit pipe security descriptor. Microsoft documents that a default named-pipe DACL grants read access to Everyone and the anonymous account. Where the product must isolate terminal sessions, include the active logon SID in the authorization decision; a user SID alone spans that user's sessions. Reject remote clients at pipe creation and claim the first pipe instance to prevent remote access and pipe-name squatting.
- Use byte-mode pipes for the protocol's length-prefixed byte stream. The prototype uses overlapped Tokio handles, a five-second frame deadline, four pipe instances, and at most three request workers. A separate Windows client open uses individual access bits because generic write maps to `FILE_CREATE_PIPE_INSTANCE`.
- The production desktop client compares the pipe server PID with `QueryServiceStatusEx` for the installed `FocusGuardService` before sending a request. It requires `SERVICE_QUERY_STATUS` on that service object; preserve this read-only right for the interactive owner SID when the installer hardens the service DACL. The local custom-host integration path checks a known process ID and does not exercise the SCM path.
- The prototype checks the user SID, but not the logon SID. Multiple terminal sessions belonging to the same Windows account are therefore not isolated yet. With an identification-level client token, the SCM service account must have `SeImpersonatePrivilege` when it differs from the caller; the local console tests use the same identity and do not verify that service-account path. Verify this and fail service startup clearly if the configured account cannot authenticate clients.
- Use a versioned typed protocol with a strict maximum message size. `focuser-app::protocol` caps serialized payloads at 1 MiB and returns a correlated `response_too_large` error instead of dropping an oversized result. The production `focuser-client` transport checks the service PID through SCM before it sends a request and rejects mismatched response IDs. Its custom-host test path pins the server process ID. Queries and exports that can exceed this cap still need pagination or bounded ranges before the UI moves to the service.
- Expose only reviewed commands through the service dispatcher. The current allowlist excludes the UI-only app-icon loader, which resolves caller-supplied filesystem paths; future command variants are denied until reviewed. Never expose arbitrary SQL, filesystem paths, shell commands, or a service-stop command.
- Every client request is untrusted. The service checks persisted lock state and validates fields before committing a transaction. It commits durable state before applying external effects, then reports both policy and enforcement status to the UI.
- Browser HTTP and UI pipe requests converge on the same service-side command layer. The browser endpoint cannot be a second policy implementation.

## Privileges and enforcement

The service needs enough authority to update the shared Windows hosts file and inspect or stop blocked processes in its supported sessions. The SCM host resolves `NT SERVICE\FocusGuardService`, explicitly checks that the SID is enabled in its process token, initializes the command context, and creates/probes a second pipe instance before reporting `Running`. The installer must enable the unique service SID with `SERVICE_SID_TYPE_UNRESTRICTED` or `SERVICE_SID_TYPE_RESTRICTED`. Never grant full pipe rights to the shared LocalService account SID; evaluate candidate service accounts only after the unique service SID and privilege path pass disposable-VM tests.

Begin with service-owned hosts-file domain fallback and per-session process checks. Hosts edits are marked, deterministic, and idempotent; cleanup removes only the FocusGuard section. URL paths, search patterns, and page rules remain extension features. Hosts filtering does not defeat DoH, VPNs, proxies, alternate browsers, or local administrators.

Do not add a kernel driver to the first service milestone. Evaluate user-mode Windows Filtering Platform integration separately after service lifecycle, ACLs, recovery, and rollback are proven. WFP rules still do not provide URL path semantics and any persistent filter needs a tested removal path.

## SCM lifecycle and installer

- Install/configure/start the service only from an elevated installer action. Set service DACLs so a standard user cannot stop, reconfigure, or delete it; administrators remain able to recover the machine.
- Configure bounded SCM recovery restarts and emit useful event-log diagnostics. At start, load and validate committed state, reapply hosts policy, initialize process/session tracking, then accept pipe/API clients.
- On graceful stop, preserve active policy while a lock remains. On uninstall or explicit recovery, use a separate admin-authorized cleanup action that removes only FocusGuard-owned artifacts. Preserve the database unless the user selects deletion.
- Installer upgrade rollback and uninstall must handle partial install, a running service, stale hosts entries, corrupt database, and service startup failure. Before service startup it must stop and confirm exit of any already-running local UI, then replace or update the `/rl highest` logon task with an unelevated service-client task. Verify its principal and launch mode in a disposable VM; the old elevated task must not run alongside the service after migration.

## Process identity prerequisite

`crates/focuser-common/src/process_identity.rs` is a shared Windows-only process-identity primitive, not an active blocker. It snapshots PID, Windows session ID, owner SID, full image path/name, and process creation time. The session ID is queried from the token belonging to the opened process handle, not by a second PID lookup. Before termination it opens a new handle, re-reads those fields, checks the configured owner SID, and terminates through that same validated handle. It rejects PID reuse, a different account, session 0, the service's own PID, and FocusGuard executable names. The identity is serializable for a future service-to-session helper protocol. Windows tests exercise the current test process plus a copied, sacrificial test executable; they verify successful termination of that child and rejection of mismatched owner, stale creation time, and protected targets.

This does not yet select active WTS sessions or run from the SCM service. A service in session 0 cannot use the desktop's existing `EnumWindows`/`WM_CLOSE` flow to offer a save prompt in a user's session. App-rule commands remain disabled, and the live service continues to enforce only hosts-file domain rules. Before enabling app rules, add active-session selection and a per-session interactive helper for graceful close and grace-period handling, then verify it with a disposable GUI process in a VM. The local sacrificial-process test is not evidence of service-account access or cross-user isolation.

## App close helper boundary

Keep process selection, policy evaluation, the 30-second close deadline, and final identity-revalidated termination in the service. A helper running in each supported user session should only validate a close request against the shared process identity and post `WM_CLOSE` from that desktop, so an application can offer its normal save prompt. Do not trust a helper-supplied process list or blocking decision. Use a separate, authenticated helper pipe; bind each request to the connecting process's actual SID and session from the pipe client PID. If a helper is absent or disconnected, the service must retain the full close grace and surface the helper gap in enforcement health; it must not interpret a missing desktop response as “no window.”

The service account and helper supervision path are still undecided. `WTSQueryUserToken`/`CreateProcessAsUser` would require an appropriately privileged LocalSystem service, while the current scheduled logon task is not a service-owned helper supervisor. Keep app-rule mutation commands disabled until the chosen launch path, per-session behavior, and fallback are tested under the installed SCM service in a disposable VM.

## Implementation sequence

1. The shared command layer and lock-preserving mutation tests already live in `focuser-app`; its `protocol` module supplies typed, versioned, bounded wire frames. Async framing, an SCM-PID-authenticated Windows client, and transport-level peer authorization now exist; expand identity/session and lifecycle coverage.
2. Add a Windows-only service executable and named-pipe server; the smoke host and opt-in persistent exact-domain hosts-policy prototype are implemented and tested without installing it on the development host. SCM startup resolves the unique service SID and creates/probes pipe instances before reporting `Running`, but this path is not installed or end-to-end tested.
3. The desktop service screen and command transport are implemented for block-list and enabled-domain management. Process identity and safe revalidation primitives are implemented, but the service does not yet enforce app rules. Add active-session selection, a per-session close helper, and app-rule coverage; then integrate the loopback extension API, migrate existing policy into service-owned storage, and complete stop/handoff for existing local UI processes before making service mode the installed Windows default.
4. Add service installation, ACLs, recovery actions, data migration, and admin cleanup to the installer only after the service and pipe tests pass.
5. Run the full installer and behavior matrix in a disposable Windows VM. Treat each supported Windows version, standard-user boundary, and administrator boundary as separate evidence.

## Required VM checks before a release

- A clean install starts the service before login; reboot restores the same locked policy before the UI launches.
- The UI may close or crash without stopping enforcement. Forced service crash causes SCM recovery and safe policy reapplication.
- A standard user cannot stop/reconfigure/delete the service, edit service-owned state, or connect to the pipe from another SID. Administrators can use documented recovery.
- Pipe framing, oversized input, malformed commands, unauthorized SIDs, duplicate clients, timeout, and service shutdown are tested.
- Both launch orders for local and service-client UIs are mutually exclusive; the owner lock releases after exit/crash; a registered-but-stopped service never re-enables local enforcement.
- Extension blocking works with the UI closed; missing extension and unsupported/private browser behavior is visible and accurately described.
- Schedule boundaries, clock changes, sleep/resume, lock expiry, DNS cache, DoH/VPN/proxy, alternate browser, and app path/rename cases are exercised.
- Upgrade rollback, corrupt database recovery, service removal, and hosts cleanup preserve unrelated entries and do not strand users offline.

## Security limit

This design aims to keep enforcement alive and make casual bypass harder for a standard user when an administrator has installed and configured the service. It cannot protect the device from its local administrator or owner, alternate boot media, another operating system, or physical access. A service is a reliability boundary and a privilege boundary; it is not tamperproof security.
