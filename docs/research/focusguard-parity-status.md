# FocusGuard feature-parity status

Scope: publicly documented Cold Turkey Blocker functionality, using the installed 4.9 binary only as an identity reference. The existing [REA evidence](cold-turkey-rea-evidence.md) is static metadata, not behavior evidence. The implementation must remain original, avoid Cold Turkey assets/source, and not bypass paid licensing. “Unknown” below is an open requirement, not a pass.

The functional checklist comes from the [public evidence ledger](cold-turkey-public-evidence.md). Current FocusGuard claims come from [README](../../README.md), [PROGRESS](../../PROGRESS.md), and the [Windows service design](../design/windows-service.md).

| Function group | Current evidence in FocusGuard | Status | Evidence still needed |
|---|---|---|---|
| Website domains and exceptions | The Windows service writes each exact domain and its `www` form to the hosts file. | Partial | Reconcile wildcard, arbitrary subdomain, allowlist/exception, category, and whole-internet semantics across the core, extension, service, and macOS. Test DNS behavior and recovery on each supported OS. |
| URL paths, search terms, channels, embedded pages | Page-level matching is assigned to the optional browser extension. | Partial | Real Chrome, Firefox, and other supported browser sessions; path/search/channel/embedded-page matching; incognito and inactive-tab behavior; clear failure state when the extension is absent. |
| Application blocking | Windows service handles a limited executable-name rule after a fixed 30-second grace period. The service UI/IPC cannot edit app rules; per-app allowances and path/title/bundle-ID matching are unsupported there. macOS local desktop rules support executable name, path, and bundle ID from the app's `Info.plist`; they stop with the desktop process, and service mode remains domain-only. The Mac bundle-ID path has source tests but no Mac runtime result yet. | Partial | Extend service app policy and enforcement, preserve allowance semantics, add a save-friendly close flow, and test matching, persistence, restart, and multi-user behavior on each OS. |
| Continuous, timed, weekly, and automatic starts | The shared engine has schedules; the Windows service is intended to retain scheduled website rules across UI closure. | Partial | Test timezone/DST, overnight intervals, sign-in/wake starts, next-schedule starts, missed starts after sleep, and restart recovery. |
| Lock modes | The app protects its autostart setting while service protection is active. Full timer, time-range, schedule, restart, password, text, and delay behavior is not established by the current release notes. | Open | Verify each documented lock against settings edits, app restart, service restart, reboot, update, and uninstall; provide explicit recovery behavior. |
| Breaks, Pomodoro, allowances, rewards, sessions | Extension/service support normal and shared allowance telemetry; service app rules do not support allowance-backed behavior. | Partial | Validate each break/allowance/reward/session rule against browser and app activity, multi-profile accounting, service downtime, and reboot. |
| Device blocks | No current release evidence establishes lock, logoff, or shutdown behavior. | Open | Implement and test each requested action, cancellation path, scheduling interaction, and recovery screen on Windows and macOS. |
| Usage statistics and data export | Block reports and visit statistics still rely on the desktop UI's local API. | Partial | Keep statistics correct when the UI closes; test app/web usage totals, private windows where supported, deletion, export, and migration. |
| Affected users and policy ownership | The Windows installer binds policy to one selected interactive account; multi-user policy selection is not established. | Partial | Define and test per-user policy semantics, isolation, sign-in switching, and helper authorization on Windows and macOS. |
| Strictness and bypass controls | Several service-mode settings are intentionally unsupported. No administrator-resistance claim is supported. | Open | Inventory each published strictness control, implement only with OS-supported boundaries, and test/do not overstate behavior. |
| CLI and automation | A FocusGuard CLI exists and is bundled as a Tauri sidecar. | Open | Compare commands and observable behavior against the product's public CLI documentation; test invalid input and locked-state behavior. |
| Browser packaging | Chrome/Edge/Firefox registration and archive builds exist; browser store submissions and a real installed-browser test do not. | Partial | Test real browsers and native messaging on supported Windows/macOS versions; complete store identity and review separately. |
| macOS desktop and enforcement | Source configures a macOS 13+ SMAppService approval/status panel, a bundled LaunchDaemon and authenticated Unix socket, protected system paths, and first-run SQLite backup from the console user's database. Approved service mode can maintain exact-domain website hosts rules; local desktop mode now matches app bundle IDs from `Info.plist`, while service mode does not enforce app rules. The Mac-specific code and bundle have not yet been built or exercised on a Mac; the Apple-target check on this Windows host stops before project code because `cc` is unavailable. | Partial | Build the helper and app bundle on macOS Intel and Apple Silicon; test bundle matching, migration, approval/denial, close/crash/reboot/wake, user switching, update, hosts restoration, and uninstall in a disposable Mac VM; sign and notarize release artifacts. |
| PublikHQ listing and API | No listing or built-app proof has been completed. Source review has not found an AI feature. | Open | Finish the outside-service inventory, derive listing metadata from the release, verify whether any Publik-covered product is actually needed, then follow the single approval step before listing. |

## Completion rule

Do not call the project feature-complete based on compilation, package generation, a type/member name, or a single-platform test. Every row needs a source path and behavior test at the stated platform scope. Keep the public feature evidence's documentation disagreements and unknown runtime behavior visible rather than guessing.
